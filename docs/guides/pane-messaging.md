# 파인 간 통신 — 사용법과 장애 대응 기록

- 최초 작성일: 2026-09-18
- 현행 설명 정리일: 2026-11-10

일상 사용법·현재 코드의 동작·한계를 먼저 안내하고, 뒤에 당시 장애 연혁을 보존한다.
현재 설명은 [bin/say](../../bin/say)와 [setup-team.sh](../../setup-team.sh)를 대조한 것이며, 이번 문서 정리에서 실기동을 재검증하지 않았다.

## 사용법

팀 pane에서는 역할명이나 pane 번호로 보내고, 팀 밖 셸에서는 세션명까지 지정한다.
메시지 본문은 영어로 간결하게 쓴다. 상세 보고처는 각 역할 지침을 따른다.

```bash
say lead "[backend] Implementation complete."
say :0.0 "[backend] Tests passed."
./bin/say team1:lead "[backend] Implementation complete."
```

상대가 작업 중이면 큐에 넣고 즉시 반환하므로 발신자는 기다리지 않는다.
작업을 즉시 중단시켜야 할 때는 `SAY_NOWAIT=1 say backend "Stop the current task."`로 큐를 우회한다.
다음 담당자에게 넘긴 사실만으로 lead에 사본을 보내지 않는다. 차단·사용자 결정 필요·범위 변경은 종결 전에도 보고한다.

## 현재 동작

### 유휴 판정

`bin/say`의 `is_busy`가 busy 마커와 화면의 경과시간 스피너를 함께 확인한다.
구현 원문은 링크한 코드에 있으며, 여기에 별도 함수 사본을 유지하지 않는다.

- busy 마커가 있고 경과시간 스피너가 보이면 작업 중으로 판단한다. 마커가 30분 이상 남으면 회수한다.
- 스피너가 없으면 인터럽트 문구 또는 마커 생성 후 45초 유예 경과를 기준으로 남은 마커를 회수한다. 생성 직후 스피너 렌더링 전에는 작업 중으로 본다.
- 마커 디렉터리가 있으나 해당 마커가 없으면 유휴로 본다. 디렉터리 자체가 없는 세션에서는 화면 스피너 검사로 폴백한다.
- `deliver`가 전송 시 busy 마커를 직접 생성한다. Claude 턴 시작 훅도 busy를 기록하며, 두 공급자의 Stop·SessionStart 훅은 남은 busy를 정리한다.

### 큐와 전송

| 상태 | 동작 |
| --- | --- |
| 유휴 + 빈 큐 | 즉시 전송 시도 |
| 작업 중 | 큐에 적재하고 반환 |
| 유휴지만 기존 큐가 있음 | 기존 큐 뒤에 적재 |
| `SAY_NOWAIT=1` | 큐를 우회해 즉시 전송 |

상태 마커 키는 tmux의 세션·pane 고유 ID를 사용한다. 큐 키는 해석된 논리 주소(`세션:창.pane`)를 사용하므로 같은 주소로 재기동한 팀에서도 큐를 다시 처리할 수 있다.
기본 경로는 `$HOME/.cache/team-busy`, `team-say`, `team-say-queue`이며 각각 `SAY_BUSY_DIR`, `SAY_REPORT_DIR`, `SAY_QUEUE_DIR`로 바꿀 수 있다.

pane별 watcher와 큐 변경은 `mkdir` 락으로 조정한다. watcher는 3초 간격으로 유휴를 확인하며 대기에는 상한을 둔다.
전송 실패는 항목별 최대 3회 시도하고, 계속 실패하면 `team-say-queue/dropped.log`에 기록한 뒤 항목을 제거한다.
Stop 훅은 busy 정리 후 `say --drain-one`을 예약하고, 팀 기동 시에도 남은 큐 처리를 재개한다.

### 보고 마커와 종료 신호

보고 마커는 수신자를 구분하지 않는 ‘이번 턴에 보고했는가’ 상태다. `say`가 큐에 적재하거나 즉시 전송 경로를 처리할 때 기록한다.
Claude·Codex 모두 생성된 `UserPromptSubmit` 훅이 보고 마커를 초기화한다.
lead 외 팀원의 Stop은 마커가 있으면 소비하고, 없으면 lead에 미보고 종료 신호를 보낸다.
lead의 Stop은 자기 자신에게 종료 신호를 보내지 않는다.

## 한계와 확인 방법

- busy 판정에는 화면 문구와 시간 기준이 포함된다. 크래시·인터럽트·렌더링 지연에서 완전한 작업 상태 보장은 어렵다.
- 큐 적재 성공이 최종 수신을 보장하지 않는다. 전송 경고, 남은 큐, `dropped.log`와 해당 pane 상태를 확인한다.
- watcher가 빈 큐를 확인한 뒤 락을 해제하기 직전 새 메시지가 들어오는 짧은 경합에서는 다음 `say`·Stop·재기동의 drain까지 전달이 지연될 수 있다.
- `tmux send-keys` 직접 실행은 큐를 우회한다. 팀 pane 간 전달은 `say`를 사용한다.
- 자동 미보고 신호가 오면 lead는 해당 pane만 확인한다. 정상 흐름에서는 반복 폴링하지 않는다.

## 과거 장애 연혁

이하 타임라인·실패 분석은 각 사건 당시의 역할·경로·구현을 보존한 기록이다.
옛 함수·명령 예시와 ‘현재’, ‘이 커밋’은 당시 상태를 가리킨다. 현행 사용법은 위 절을 따른다.

### 관통하는 원칙

**모델이 실행하는 명령의 성실성에 기대지 않는다.**

같은 판단이 두 번 반복됐다. Enter 누락은 `say` 래퍼로, 보고 누락은 harness가
실행하는 Stop 훅으로 막았다. 둘 다 "모델이 잘 하도록 지침을 고친다"가 아니라
**모델이 잊어도 결과가 보장되는 구조로 바꾼 것**이다.

지침 강화가 통하지 않는 이유는 실패가 의지의 문제가 아니어서다. `tmux send-keys
-t :0.0 "메시지" Enter`에서 Enter는 문자열이 아니라 별개 인자다. 문장을 조립하다
빠뜨리기 쉬운 형태고, 실제로 자주 빠졌다.

### 각 실패의 내용

#### 0단계 — `send-keys` 직접 실행 (`617416a`, `f07a20d`)

최초 `setup-team.sh`(`617416a`)는 tmux 파인 6개를 띄우고 각각 `claude`를 실행하는
게 전부였다. 파인 이름은 tmux 타이틀에만 있었다(`"민준 아키텍트"`).

통신 규약은 곧이어 `f07a20d`의 CLAUDE.md와 함께 들어왔다. **처음부터 통신 수단을
정해두고 시작했고**, 그 수단이 **모델이 `tmux send-keys`를 직접 실행**하는 것이었다.
파인 번호와 명령 형태를 표로 명시했다.

```
CLAUDE.md:12  | 민준 (설계) | team:0.1 | tmux send-keys -t team:0.1 "..." Enter |
CLAUDE.md:13  | 지훈 (조사) | team:0.2 | tmux send-keys -t team:0.2 "..." Enter |
CLAUDE.md:20  ## 진행 확인
CLAUDE.md:21  tmux capture-pane -t team:0.{N} -p | tail -5
```

즉 이후 단계들은 통신을 뒤늦게 도입한 과정이 아니라, **처음 정한 규약이 실제로
지켜지지 않는다는 것을 확인하고 강제 수단을 붙여간 과정**이다.

#### 1단계 — 역할별 지침 분리 (`2cf3e6e`)

0단계의 CLAUDE.md는 lead 전용이었는데 6개 파인이 이걸 똑같이 물려받았다. architect
파인도 developer 파인도 "팀원에게 배분하라"는 lead 지침을 읽는 상태였다.

역할 지침을 `team/*.md`로 쪼개 `--append-system-prompt`로 파인마다 자기 것만
주입하도록 바꿨다. 통신 수단은 그대로 `send-keys`이고, 각 역할 문서가 자기 보고
대상을 명시하는 형태가 됐다.

```
lead.md:21      | architect (설계) | team:0.1 | tmux send-keys -t team:0.1 "..." Enter |
architect.md:29   tmux send-keys -t team:0.0 "lead, 아키텍처 설계 완료: [요약]" Enter
reviewer.md:34    tmux send-keys -t team:0.1 "architect, [파일명] 리뷰 완료: [핵심 소견]" Enter
```

#### 2단계 — Enter 누락 (`6a311a6`)

지침에 `Enter`가 분명히 적혀 있는데도 누락됐다. 누락되면 메시지가 상대 파인
입력창에 텍스트로 남고 전송되지 않는다. **보낸 쪽은 보고를 마쳤다고 착각하고,
받는 쪽은 아무것도 모르는** 상태가 된다.

`bin/say`를 만들어 Enter를 항상 붙였다. 초기 버전은 39줄이고, 타겟 해석(파인
번호·역할 이름 양쪽)과 `send-keys -l` 리터럴 전송, 입력창 반영을 기다리는
`sleep 0.3`이 전부였다.

#### 3단계 — 보고를 아예 안 함 (`3dbfd40`)

`say`가 있어도 파인이 **호출 자체를 하지 않는** 경우가 남았다. 원인이 둘이었다.

**architect가 보고를 삼킴.** researcher/reviewer는 "architect에게만 보고, lead
직보고 금지"였는데, architect.md에는 받은 보고를 어떻게 처리하라는 지침이 없었다.
보고가 architect에서 끊겼다.

**보고가 응답 텍스트로만 끝남.** 역할 문서가 "팀장에게 보고"라고만 적어둬서, 파인이
`say`를 실행하지 않고 자기 화면에 "완료했습니다"라고 출력하고 끝냈다. 그 텍스트는
파인 밖으로 나가지 않는다. 지금 CLAUDE.md에 남은 경고가 여기서 나왔다.

> **응답 텍스트에 "완료했습니다"라고 쓰는 것은 보고가 아니다**

대응으로 lead.md에 폴링 백스톱을 넣었다. 30~60초 간격으로 미완료 파인을 캡처해
확인하는 방식이다. **이것이 나중에 토큰 비용 문제의 출발점이 된다** — 폴링 1회가
lead의 새 유저 턴이라 그때까지의 컨텍스트 전체가 재청구되고, lead는 모든 보고가
모여 컨텍스트가 가장 빨리 불어나는 파인이다. 이후 Stop 훅으로 대체되는 과정은
[token-cost.md](token-cost.md) 참조.

#### 4단계 — 신호가 전부 :0.0으로 감 (`47a3b2d`)

Stop 훅 커맨드 안의 `tmux display-message -p '#{pane_index}'`가 자기 파인이 아니라
**그 시점의 활성 파인 번호**를 반환했다. 훅 프로세스에 `TMUX_PANE`이 전달되지 않기
때문이다. lead가 활성 상태이던 탓에 모든 파인이 lead 자신인 :0.0으로 종료 신호를
보냈고, lead는 어느 파인이 미보고인지 특정할 수 없었다.

파인 번호를 호출 시점의 `$pane`에서 직접 가져오도록 고쳤다.

같은 커밋에서 **중복 신호 억제**도 넣었다. 본 보고와 종료 신호가 둘 다 도착하면
lead 턴을 한 번 더 태운다. `say`가 `$HOME/.cache/team-say/{파인번호}`에 마커를 남기고,
Stop 훅은 마커가 있으면 신호를 생략하고 마커만 소비한다. 훅이 부르는 `say`는
`TMUX_PANE`이 없어 마커를 남기지 않으므로, 신호가 자기 자신을 억제하지 않는다.

#### 5단계 — 전송 검증 (`fafc2d6`)

Enter를 붙여도 무시되거나 대상 지정이 틀릴 수 있다. 전송 후 상대 입력창에 메시지가
그대로 남아있으면 경고하고 실패 처리한다.

```bash
probe="${msg:0:40}"
if [ -n "$probe" ] && tmux capture-pane -t "$pane" -p | tail -5 | grep -qF -- "$probe"; then
    echo "say: WARNING - '$pane'에 메시지가 전달되지 않고 입력창에 남아있는 것으로 보입니다"
```

메시지가 길면 입력창에서 줄바꿈되므로 앞 40자만 검사한다.

#### 6단계 — 쪼개짐과 끼어들기 (`c37ac6f`)

두 문제를 함께 고쳤다. 이 커밋에서 `say`가 62줄에서 166줄로 늘었다.

**쪼개짐.** `send-keys -l`이 줄바꿈을 그대로 밀어넣는데 Claude Code 입력창은 그것을
Enter(전송)로 해석한다. 여러 줄 메시지가 **줄 수만큼 별도 턴으로 쪼개져** 도착했다.
받는 쪽은 첫 줄만 보고 작업을 시작하고 나머지 줄은 그 작업 도중의 중간 입력이 된다.
홉 수도 줄 수만큼 배로 늘었다.

줄바꿈을 `" / "`로 치환해 항상 한 번에 보낸다. 공백으로만 합치면 "에러 수정" +
"테스트 추가"가 "에러 수정 테스트 추가"로 뭉개지므로 구분자를 남긴다. 탭도
자동완성으로 해석될 수 있어 공백으로 바꾼다. 5줄을 넘으면 파일로 넘기라고 안내하되
중단하지는 않는다.

**끼어들기.** 작업 중인 파인에 보내면 그 작업 도중의 중간 입력으로 꽂힌다. 문제는
**5단계의 전송 검증이 이걸 못 잡는다**는 점이다 — 검증은 "입력창에 남아있는지"만
보는데, 이 경우 전송은 성공했다. 검증을 통과하면서 엉뚱한 맥락에 꽂힌 상태가 된다.

전경에서 기다리는 건 답이 아니었다. 실제 작업은 수 분씩 걸리는데 그동안 발신 파인이
멈춘다. 그래서 **대기를 백그라운드로 넘기고 즉시 반환**하는 큐를 만들었다.

#### 7단계 — 오탐과 무한 대기 (`3b90a37`)

큐가 새 문제를 만들었다.

**오탐.** 처음엔 화면 전체에서 `esc to interrupt`를 찾았다. 그런데 파인이 say 동작을
설명하거나 로그를 인용하면 그 문구가 **본문 텍스트로** 화면에 나타난다. 유휴인데
작업 중으로 오판하고, 문구가 화면에 남아있는 동안 대기 루프가 계속 돈다.
`tail -5`로 하단만 보게 좁혔다.

**무한 대기.** 감지가 어떤 이유로든 계속 참이면 메시지가 영영 전달되지 않는다.
600회(30분) 상한을 두고, 넘으면 바쁘더라도 보낸다 — 늦게라도 보내는 편이 낫다.

#### 8단계 — 갈라짐과 유실 (`6c71244`, `703aa7d`)

큐 자체의 무결성에 두 결함이 있었다.

**갈라짐.** 큐 파일 이름을 `$pane` 문자열 그대로 만들었다(`":0.0"` → `_0_0`). 그런데
같은 파인을 가리키는 호출이라도 `$pane` 문자열이 갈렸다 — 파인 내부에서 `say :0.0`을
부르면 session이 비어 `":0.0"`이고, Stop 훅이 부르는 `say team1:0.0`은 session이
`"team1"`이라 `"team1:0.0"`이다. 문자열이 다르니 큐 파일도 `_0_0`과 `team1_0_0`으로
갈라지고, 감시 프로세스도 각각 떠서 **파인당 하나여야 할 큐와 워처가 둘이 됐다.**
순서 보존과 워처 단일화 전제가 그대로 깨진다.

`tmux display-message`로 실제 `세션:윈도우.파인` 인덱스를 해석해 그걸 키로 쓴다.
두 호출 모두 같은 파인을 가리키면 같은 인덱스로 정규화되어 큐 파일이 하나로 합쳐진다.
해석에 실패하면(파인이 이미 사라졌다 등) 기존 `$pane`으로 폴백하는데, 존재하지 않는
세션을 지정하면 tmux가 실패(exit 1) 대신 빈 필드 `":."`를 exit 0으로 돌려주는 경우가
있어, 세 필드가 모두 채워졌는지 정규식으로 확인한 뒤에만 해석 결과를 쓴다.

**유실.** 큐 파일을 락 없이 "읽고 나서 썼다." 그 사이 다른 프로세스가 끼어들면
메시지가 **조용히** 사라진다 — 아무도 에러를 보지 못한다. 두 지점이 있었다.

- 워처가 dequeue용 스냅샷(`tail -n +2`)을 뜬 뒤 `mv`로 큐를 덮어쓰는 사이, 다른 say
  호출이 append하면 그 메시지가 덮어써진다.
- 워처가 큐가 비었다고 판단해 `rm`하는 순간 새 메시지가 append되면 그 메시지째
  지워진다. 게다가 그때 election `lock_file`은 아직 살아 있어 **새 워처도 뜨지 않아**,
  사라진 메시지는 다음 say 호출이 있을 때까지 영영 복구되지 않는다.

`mkdir`은 원자적이라 이걸 짧은 임계구역 락(`queue_lock`/`queue_unlock`)으로 쓴다.
append와 '빈 큐 판정+rm+dequeue'를 같은 락으로 상호배제해, 읽은 시점과 쓴 시점 사이에
끼어들 틈을 없앤다. 응답 없는 락은 죽은 프로세스가 남긴 것으로 보고 5초 후 강제
회수한다 — `is_busy` 대기 상한과 같은 취지로, 무한 데드락보다 늦은 진행이 낫다.

#### 9단계 — 화면 문구 오탐 (`ae6efc5`)

7단계에서 하단 5줄로 좁혔는데도 남는 오탐이 실측으로 나왔다.
`--dangerously-skip-permissions` 모드 파인은 **유휴 상태에서도** 하단
힌트줄에 "esc to interrupt"가 잔류하는 경우가 있다 — 스피너는 없고 `❯ `
빈 입력줄인데 힌트줄만 안 지워진다. 본문 노출과 달리 tail 범위를 더
좁혀도 걸러지지 않는다(애초에 상태줄 자체가 문제라서).

화면 문구 대신 **harness가 보장하는 실제 턴 경계**로 옮겼다.
`UserPromptSubmit` 훅이 턴 시작 시 `$HOME/.cache/team-busy/{pane_id}` 마커를
찍고, `Stop` 훅이 턴 종료 시 지운다. `is_busy()`는 이제 화면을 캡처하지
않고 이 마커 파일의 존재만 본다. 훅 인프라 없이 뜬 세션(마커 디렉터리
자체가 없는 경우) 대비로, 스피너 경과시간 패턴(`(15s ·` 형태, 고정
포맷)을 보는 폴백을 남겨뒀다 — 스피너 문구 자체는 무작위라 못 쓰지만
이 시간 표시는 항상 붙는다.

#### 10단계 — 마커가 1비트인데 한 턴에 여러 번 보고한다 (이 커밋)

9단계까지는 "메시지가 전달되는가"를 다뤘다. 10단계는 그 다음 문제다 —
**메시지는 전부 도착했는데 lead의 턴이 낭비된다.**

commerce-data-platform Phase 6 세션(`.claude-logs`, lead 56턴)을 실측했다.

먼저 확인한 것: architect·reviewer가 lead로 보낸 29건은 **전부 도착했다.
누락 0건.** 3단계에서 세운 Stop 훅 백스톱은 제대로 동작하고 있었다.

문제는 반대 방향이었다.

**증상 1 — 보고했는데 "미보고" 신호가 간다.** 종료 신호 4건이 나갔는데
4건 모두 해당 파인이 그 턴에 실제로 보고를 한 뒤였다. reviewer 기록:

```
14:02:00  say architect "[reviewer] fact_orders schema..."   ← 마커 찍힘
14:02:08  say lead "[reviewer] fact_orders FK Test..."        ← 같은 마커 덮어씀
14:04:41  [reviewer] (자동) 응답 종료 — 미보고 시 확인 필요    ← 오탐
```

`record_marker`는 발신 파인 기준 키로 파일 **하나**를 찍는다(수신자 구분
없음). Stop 훅은 그 파일이 있으면 소비(`rm`)하고 신호를 건너뛴다. 즉
마커는 "이번 턴에 보고했나" 1비트인데 **턴 경계에서 초기화되지 않아**,
한 턴에 두 번 보내면 이전 턴에 소비된 상태가 그대로 넘어온다.

`UserPromptSubmit` 훅에 `rm -f $HOME/.cache/team-say/{state_key}`를 추가해 턴
시작마다 비운다. 이 훅이 없는 Codex 파인은 Stop 훅의 삭제가 유일한
초기화 지점이라, 그쪽 주석에 그 사실을 명시했다.

**증상 2 — lead 턴의 35%가 보고를 읽기만 하고 끝난다.** 56턴 중 19턴이
툴 호출 0건이었다. 전문을 대조하니 두 부류였다.

_FYI 사본(7건)_ — 본문에 "developer에 전달했다", "architect 경유함",
"지시했다"가 박혀 있다. 보고자가 **이미 다음 사람에게 넘겼고** lead에는
사본을 보낸 것이다. lead가 할 일이 구조적으로 없다.

출처는 지침이었다. `team/reviewer.md`에 "**동시에 lead에게도 리뷰가
끝났음을 알린다**"가 있었다. 모델이 과하게 보고한 게 아니라 시킨 대로
한 것이다.

_중간 상태 보고(9건)_ — "보류 기록 완료", "체크박스 갱신 확인", "재확인
완료". 특히 같은 사안(Watermark Guard)에 developer·reviewer·architect가
**각자 따로** lead에 보고해 3턴이 한 사안에 쓰였다.

세 가지를 고쳤다.

1. **FYI 사본 폐지** — `reviewer.md`의 "동시에 lead에게도" 지침을 삭제하고
   "작성자가 수정을 마치면 작성자가 직접 보고한다"로 바꿨다. 설계 판단
   경유 구간에도 같은 금지를 명시했다.
2. **보고 시점 이동** — architect는 사본을 **없애면 안 된다**(유일한 중간
   노드라 삼키면 lead가 영영 모른다). 문제는 사본이 아니라 시점이었다.
   지시를 넘긴 시점에는 결과가 없으므로, 그 지시의 결과까지 확인한 뒤
   한 번에 보고하도록 바꿨다. 자기 손에서 끝나는 산출물(설계 문서·계획)은
   완료 즉시 보고를 유지한다.
3. **공통 규칙** — CLAUDE.md/AGENTS.md 보고 규칙에 "다음 담당자에게 직접
   전달한 건은 사본 없음", "작업 단위가 끝날 때 한 번만", "한 턴에 lead로
   두 번 이상 `say` 하지 않는다"를 넣었다. 마지막 항목은 증상 1의 마커
   경합을 지침 쪽에서도 막는다.

**검증.** 팀 재시작 후 세 역할이 모두 도는 작업(보류됐던 Dimension PK
Test 건)을 한 번 돌렸다.

| ------------------------ | --------- | ------------ |
| FYI 사본                 | 7         | 0            |
| 종료 신호 오탐           | 4         | 0            |
| 역할 보고 중 툴 호출 0턴 | 16        | 1(종결 보고) |

architect 발신 3건 중 lead로 간 것은 1건뿐이었다 — 구현 지시와 중간
검수는 developer에만 가고, lead에는 판정이 끝난 뒤 한 번. 의도한 경로다.
